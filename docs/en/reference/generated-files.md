# Generated Context Files

`build82` generates structured Markdown files directly in your Moodle installation. They let the AI assistant understand your code architecture without reading thousands of lines of raw PHP.

Every generated file lives under a `.build82/` directory — at the Moodle root for global files, and at each plugin's root for per-plugin files. Nothing is written directly into the Moodle root or a plugin root. A file is rewritten only when it is missing or a source file is newer than it (see [Regeneration rules](#regeneration-rules)).

---

## 📂 Global Files (`{moodle_root}/.build82/`)

Generated by `init_moodle_context` and `update_indexes` (13 Markdown files plus `tags`).

| File | Description | Regenerated when newer than the output |
|---|---|---|
| `AI_CONTEXT.md` | Installation summary: version, directory purposes, key `lib/` APIs, coding guidelines, links to the other index files | every plugin `version.php` |
| `MOODLE_AI_INDEX.md` | Master index of all generated global files and of plugins that have AI context (also refreshed by `generate_plugin_context`, `plugin_batch` and the watcher) | every plugin `version.php` |
| `MOODLE_AI_WORKSPACE.md` | Workspace status: version, plugin counts, plugins in development, plugins with AI context | every plugin `version.php` |
| `MOODLE_API_INDEX.md` | Core `lib/` functions with summary, return type, `@since` and `@deprecated` marks | Moodle root files (see below) |
| `MOODLE_CLASSES_INDEX.md` | PHP classes, interfaces, traits and enums under `classes/` directories | Moodle root files (see below) |
| `MOODLE_CAPABILITIES_INDEX.md` | Capabilities declared in every `db/access.php` | `db/access.php` |
| `MOODLE_DB_TABLES_INDEX.md` | Tables declared in every `db/install.xml` | `db/install.xml` |
| `MOODLE_EVENTS_INDEX.md` | Event observers declared in every `db/events.php` | `db/events.php` |
| `MOODLE_PLUGIN_INDEX.md` | Installed plugins with component, type, name, version and path | every plugin `version.php` |
| `MOODLE_SERVICES_INDEX.md` | Web service functions declared in every `db/services.php` | `db/services.php` |
| `MOODLE_TASKS_INDEX.md` | Scheduled tasks declared in every `db/tasks.php` | `db/tasks.php` |
| `MOODLE_DEV_RULES.md` | Coding-standard snippets: security, database API, plugin file structure, events, tasks | Moodle root files (see below) |
| `MOODLE_PLUGIN_GUIDE.md` | Component naming, required files, `version.php` template, autoloaded class paths | Moodle root files (see below) |
| `tags` | ctags symbol index of the PHP code (`ctags -R --languages=PHP`, excluding `vendor` and `node_modules`). Skipped silently when no `ctags` executable is on `PATH` | Moodle root files (see below) |

**Moodle root files:** `version.php`, `lib/moodlelib.php` and `lib/accesslib.php` in the Moodle root.

The `db/*` sources are collected by searching the whole Moodle tree (skipping `vendor/`, `node_modules/`, `.git/` and symlinked files). The per-plugin `version.php` sources are those of the plugins found under the known plugin-type directories.

## 🧩 Files per Plugin (`{plugin_root}/.build82/`)

Generated by `generate_plugin_context`, `plugin_batch`, `update_indexes` with `include_plugins`, and the `watch_plugins` watcher. Created inside each plugin directory — for example `local/myplugin/.build82/`. All 12 files share the same sources (see [Regeneration rules](#regeneration-rules)).

| File | Description |
|---|---|
| `PLUGIN_AI_CONTEXT.md` | **Main file.** Quick reference combining metadata and per-feature counts (tables, events, tasks, services, capabilities, Hook API, classes), with links to the other plugin files |
| `PLUGIN_CONTEXT.md` | Metadata (component, type, version, requires, display name, maturity, path) and feature counts |
| `PLUGIN_STRUCTURE.md` | Directory tree (2 levels; dot-entries, `node_modules` and `vendor` omitted) and key-files checklist |
| `PLUGIN_ARCHITECTURE.md` | Class count and classes grouped by directory |
| `PLUGIN_SETTINGS.md` | Admin settings declared in `settings.php` (`admin_setting_*` entries) |
| `PLUGIN_RUNTIME_FLOW.md` | Entry points, core logic files, and a summary of classes/events/tasks/services |
| `PLUGIN_DB_TABLES.md` | Schema extracted from `db/install.xml`: tables, fields, types, keys and indexes |
| `PLUGIN_FUNCTION_INDEX.md` | Top-level PHP functions, grouped by file |
| `PLUGIN_CALLBACK_INDEX.md` | Legacy `lib.php` callbacks and Hook API registrations/definitions (Moodle 4.3+), with legacy-to-hook migration warnings |
| `PLUGIN_EVENTS.md` | Event observers registered in `db/events.php` |
| `PLUGIN_ENDPOINT_INDEX.md` | Web services, AJAX endpoints and AMD modules defined by the plugin |
| `PLUGIN_DEPENDENCIES.md` | Scheduled tasks, web services, capabilities, Hook API usage, upgrade history and hosted subplugin types |

## Other Files in `.build82/`

| File | Location | Description |
|---|---|---|
| `.indevelopment` | `{plugin_root}/.build82/` | Marker that puts the plugin under development. Contains a timestamp. Written by `generate_plugin_context`, by `plugin_batch` in `dev` mode (or with `mark_as_dev`), by `update_indexes` with `include_plugins` and by the watcher |
| `.cache.json` | `{moodle_root}/.build82/` | Persisted freshness marks of the mtime cache: `{"version": 1, "entries": {"<absolute output path>": "<timestamp>"}}`. A missing, corrupt or version-mismatched file is treated as an empty cache. Written atomically; no cross-process lock |

## Regeneration rules

Before each generator runs, the cache decides whether its output is stale:

0. The output was explicitly invalidated (by `force: true` or a watcher event) and has not been regenerated since: regenerate, regardless of file modification times.
1. The output file does not exist: regenerate.
2. The output has a freshness mark (set when build82 wrote it): regenerate only if a source file is newer than the mark; otherwise keep it.
3. No mark (or the mark was discarded in step 2): regenerate if any source file is newer than the output file's mtime; otherwise keep it.

Source files that do not exist are ignored. `force: true` on `plugin_batch`/`update_indexes` (step 0) regenerates the affected outputs even when every source is older than the output (see [Cache System](../architecture/cache-system.md)).

**Per-plugin sources** (paths relative to the plugin root; the same list is watched by `watch_plugins`):

`version.php`, `lib.php`, `locallib.php`, `settings.php`, `db/install.xml`, `db/access.php`, `db/events.php`, `db/tasks.php`, `db/services.php`, `db/upgrade.php`, `db/hooks.php`, `db/subplugins.json`, `db/subplugins.php`

Changes elsewhere in the plugin (for example files under `classes/`, `lang/` or `amd/`) do not by themselves make the per-plugin files stale.

## Editor `tags` file

build82 writes the ctags output to `{moodle_root}/.build82/tags`, and only when a `ctags` executable (universal-ctags) is on `PATH`. Vim users can point the editor at it by adding this to `~/.vimrc`:

```vim
set tags=./.build82/tags;
```

The trailing `;` makes Vim search upward from the current file's directory until it finds a `.build82/tags`, so it works from any subdirectory of the Moodle tree.

## ❓ Frequently Asked Questions

### Should I version these files in Git?

**Not recommended.** These files are generated automatically and change whenever the source code is updated. Since everything lives under a single `.build82/` directory, one line covers it:

```gitignore
# build82 context files
.build82/
```

### Do these files add weight to the server?

No. They are plain Markdown text files, usually a few KB each. Only files whose sources changed are rewritten, so later runs are fast.

### Can I edit these files manually?

Not recommended. Any manual edit is overwritten the next time the server regenerates the context. To add persistent notes for the AI about a project or plugin, use `CLAUDE.md` (Claude Code) or `GEMINI.md`/`AGENTS.md` (other clients) in the installation root. The server never touches those files.

### Why wasn't a file updated after I changed the code?

Only the source files listed in [Regeneration rules](#regeneration-rules) are compared. A change outside that list (for example inside `classes/`) does not trigger regeneration. To force an update, the simplest way is `force: true` on `plugin_batch` (for plugin files) or `update_indexes` (for global files). Alternatives:

- Touch one of the listed source files (for example `touch local/myplugin/version.php`) and run `generate_plugin_context`, or `plugin_batch` in `mode="list"`.
- Or delete the generated file (or the whole `.build82/` directory of the plugin) and run the tool again; a missing output is always regenerated.
- For global files, delete the file under `{moodle_root}/.build82/` and run `update_indexes`.

### What happened to the old flat file layout?

Files in the legacy flat layout sit directly at the Moodle/plugin root instead of under `.build82/`. Every generator run first moves any legacy file it finds into the new location — no manual cleanup needed. `doctor` reports how many legacy files are pending.
