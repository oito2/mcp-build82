# Glossary

Technical terms used in the `build82` documentation, organized alphabetically.

---

## Backend (extractor)

One of the two interchangeable parsing implementations behind most extractors: the **regex** backend (`internal/extractors`, the default) and the opt-in **tree-sitter** backend (`internal/extractors/tsbackend`). The choice is made by the `BUILD82_EXTRACTOR_BACKEND` environment variable (only the value `treesitter` switches; anything else uses regex) and is re-read on every call. Extractors that read XML or simple header lines (`schema.go`, `moodledetect.go`) and the diagnostic scans used by `doctor` have no tree-sitter counterpart.

→ See: [Extractors](../architecture/extractors.md#two-backends-one-contract)

---

## `.build82/` directory

The single directory where `build82` writes everything it generates: at the Moodle root (global `MOODLE_*.md` files, `AI_CONTEXT.md`, `tags`, `.cache.json`) and at each plugin root (the 12 `PLUGIN_*.md` files and the `.indevelopment` marker). The name is fixed. It is excluded from `release_plugin` ZIPs.

→ See: [Generated Files](../reference/generated-files.md)

---

## `~/.build82`

Configuration file automatically generated by the server when `init_moodle_context` is executed for the first time. It stores the Moodle installation path and the detected version, eliminating the need to pass this data in every session.

It is read by `internal/config` during server startup. Environment variables (`BUILD82_MOODLE_PATH`, `BUILD82_MOODLE_VERSION`, `BUILD82_MOODLE_FULLVERSION`) take priority over this file.

---

## `.buildignore`

Optional file at a plugin's root listing extra file or directory names (one per line, `#` comments allowed) to leave out of the ZIP created by `release_plugin`. Patterns are added to the fixed exclusion set (`.build82`, `.git`, `node_modules`, AI-assistant files, ...) and are matched as exact basenames at any depth.

→ See: [Tools Reference](../reference/tools.md)

---

## Component

Unique identifier of a Moodle plugin in **frankenstyle** format — `type_name`. It is the value that appears in each plugin's `version.php` and is used as a parameter in the server tools.

Examples: `local_myplugin`, `mod_quiz`, `block_html`, `auth_ldap`.

→ See: [Frankenstyle](#frankenstyle)

---

## Dev plugin

A plugin that is marked as under development, i.e. that has a `.build82/.indevelopment` marker. Dev plugins are the ones handled by `plugin_batch` in `dev` mode, listed by `list_dev_plugins`, regenerated by `update_indexes` with `include_plugins`, and watched by `watch_plugins` (up to 20 at once).

→ See: [`.indevelopment`](#indevelopment)

---

## Extractor

Internal Go package of `build82` responsible for reading and parsing a specific type of Moodle PHP file. Each extractor produces structured data that is consumed by the Generators, and (for most PHP files) has two interchangeable [backends](#backend-extractor): a regex parser (default) and an opt-in tree-sitter parser (`BUILD82_EXTRACTOR_BACKEND=treesitter`).

Examples: `schema.go` reads `db/install.xml`; `events.go` reads `db/events.php`; `api.go` reads `lib/*.php`.

→ See: [Extractors](../architecture/extractors.md) · [How the server works](./how-build82-works.md)

---

## Frankenstyle

Moodle naming convention used to uniquely identify plugins. The format is `type_name`, where `type` is the plugin type (`local`, `mod`, `block`, `auth`, etc.) and `name` is the plugin identifier in lowercase without hyphens.

Examples: `local_mytools`, `mod_checklist`, `block_coursestats`.

Frankenstyle is used as a table prefix in the database, as a PHP namespace, and as a parameter in the server tools (for example, the `plugin` parameter in `get_plugin_info`).

---

## Generator

Internal Go package of `build82` responsible for transforming the data produced by the Extractors into context `.md` files written under `.build82/`. There are two types: global generators (write to `{moodle_root}/.build82/`) and plugin generators (write inside each plugin's `{plugin_root}/.build82/`).

→ See: [Generators](../architecture/generators.md) · [Generated Files](../reference/generated-files.md)

---

## Hook API

Moodle extension system introduced in version 4.3 that progressively replaces the legacy callbacks from `lib.php`. It allows plugins to register to receive notifications of core events in a more structured way and with better PHP typing support.

`build82` detects and indexes both legacy callbacks and Hook API definitions in `db/hooks.php` and `classes/hook/`.

---

## `.indevelopment`

Marker file at `<plugin_root>/.build82/.indevelopment` (its content is only a timestamp). It is written by `generate_plugin_context` and by `plugin_batch` in `dev` mode (or with `mark_as_dev`), and only its existence matters. It is what turns a plugin into a [dev plugin](#dev-plugin).

→ See: [Uninstallation](../getting-started/uninstallation.md)

---

## Legacy files (migration)

Generated files in the legacy flat layout, sitting directly at the Moodle or plugin root instead of under `.build82/`. `MigrateLegacyFiles` moves them into `.build82/` at the start of every generation pass, and `doctor` only reports them without changing anything.

→ See: [Generators](../architecture/generators.md)

---

## MCP (Model Context Protocol)

Open standard created by Anthropic that defines how AI assistants communicate with external tools and data sources. It allows a single server to be used by any compatible client — Claude Code, Antigravity CLI, OpenAI Codex, OpenCode, and others.

`build82` is an MCP server specialized in Moodle plugin development, written in Go and distributed as a single static binary.

→ See: [What is MCP?](./what-is-mcp.md)

---

## mtime Cache

Cache mechanism used by the Generators to avoid unnecessary regeneration of files. Before rewriting a context `.md` file, the server compares the modification date (`mtime`) of the PHP source file with the corresponding `.md` file. If the PHP file has not changed since the last generation, the file is skipped. Persisted to `.build82/.cache.json`, so a server restart doesn't force a full re-scan.

To force a full regeneration, ask the assistant: _"Regenerate all indexes ignoring the cache"_. The AI will call `update_indexes` with `force=true`.

→ See: [Cache System](../architecture/cache-system.md)

---

## `PLUGIN_AI_CONTEXT.md`

Main context file generated by the server inside each plugin's `.build82/` directory. It consolidates the most relevant plugin information — architecture, database, functions, events, callbacks, and execution flow — into a single file optimized for consumption by the AI assistant.

It is the recommended entry point to start any development session on an existing plugin.

→ See: [Generated Files](../reference/generated-files.md)

---

## Prompt (MCP)

Prebuilt prompt template exposed by the MCP server that automatically injects the complete Moodle and installation context before executing a task. Unlike Tools — which execute actions — Prompts guide the AI on **how** to perform a complex task, with examples and Moodle-specific patterns.

`build82` exposes three prompts:

| Prompt            | Purpose                                        |
| ------------------ | ------------------------------------------------- |
| `scaffold_plugin` | Create the full structure of a new plugin         |
| `review_plugin`   | Review a plugin's code with configurable focus    |
| `debug_plugin`    | Debug an error with full plugin context           |

In clients that expose MCP prompts as slash commands (e.g. Gemini Code Assist's Agent mode), they're available as `/scaffold_plugin`, `/review_plugin`, `/debug_plugin`.

→ See: [Prompt Reference](../reference/prompts.md)

---

## Resource (MCP)

Structured data exposed by the MCP server via URI that the AI client reads passively as context — without requiring an explicit call from the user. Resources are updated whenever the context `.md` files are regenerated.

Examples of URIs: `moodle://api-index`, `moodle://plugin/local_myplugin`, `moodle://db-tables`.

→ See: [Resource Reference](../reference/resources.md)

---

## stdio

Default MCP transport mode where the server runs as a subprocess of the AI client, communicating via standard input and output (stdin/stdout). It does not open network ports. This is `build82`'s default mode — running it with no flags starts stdio.

→ See: [Architecture — Transport modes](./architecture.md#transport-modes)

---

## Streamable HTTP

Alternative MCP transport mode (`build82 --http`) where the server runs as an independent HTTP service. Used when Moodle is on a different machine than the one running the AI client (e.g., remote server, isolated Docker environment). Authentication via Bearer token (`--token` or the `BUILD82_TOKEN` environment variable) is optional but strongly recommended.

→ See: [Architecture — Transport modes](./architecture.md#transport-modes) · [Docker](../guides/environments/docker.md)

---

## Tool (MCP)

Executable function exposed by the MCP server that the AI assistant can explicitly call to perform an action. Unlike Resources — which are read passively — Tools are invoked on demand, usually in response to a user request in natural language.

`build82` exposes 13 tools:

| Tool                      | What it does                                              |
| -------------------------- | -------------------------------------------------------------- |
| `init_moodle_context`     | Initializes the full installation context                     |
| `generate_plugin_context` | Generates AI context for a specific plugin                    |
| `plugin_batch`            | Generates context for multiple plugins at once                |
| `update_indexes`          | Regenerates the global indexes                                 |
| `watch_plugins`           | Monitors plugins and updates context on save                  |
| `search_plugins`          | Searches installed plugins                                    |
| `search_api`              | Searches Moodle core API functions                             |
| `get_plugin_info`         | Loads the full context of a plugin into the session            |
| `list_dev_plugins`        | Lists plugins under development                                |
| `doctor`                  | Diagnoses the environment and reports server health            |
| `explain_plugin`          | Explains a plugin's architecture by section                   |
| `release_plugin`          | Packages a plugin directory into a distributable ZIP           |
| `create_plugin_skeleton`  | Materializes a new plugin's directory structure on disk        |

→ See: [Tools Reference](../reference/tools.md)

---

## Watcher

The `fsnotify`-based component started by `watch_plugins`. It watches the source files of every dev plugin (`version.php`, `lib.php`, `db/*.php`, `db/install.xml`, ...), waits 500 ms after the last change (debounce), invalidates the plugin's cache marks and regenerates its context. It lives only in memory and must be started again after a server restart.

→ See: [Cache System](../architecture/cache-system.md)
